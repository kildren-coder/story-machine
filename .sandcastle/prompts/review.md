## 铁律

- **测试前台阻塞跑，不要后台**（被自动转后台就重跑成阻塞调用）。你是串行的，
  后台化换不来并行收益，只会诱发轮询白烧 token。
- **子 agent 只用来隔离大块探索**（同步开，`run_in_background:false`）：让它读
  文件、只带结论回来；不要为并行开多个。
- **看 diff，不要 `cat` 整个文件。** 你的判断依据是改动，不是全文；整文件读多了
  上下文很快就满，越到后面判断越差。确实需要周边代码时按行号范围取。
- 沙箱里没有 vault、没有逐字稿；**不要调 `claude -p`**。你只验机械部分。

## 评审流程

1. `git log {{TARGET_BRANCH}}..HEAD --oneline` 和
   `git diff {{TARGET_BRANCH}}...HEAD` 通读全部改动。
2. 跑 `bash scripts/test.sh`，必须全绿。
3. 逐条核对 issue 验收标准：每条是否有实现、是否有对应测试、测试是否真的
   断言了该行为（警惕永真断言和只测 happy path）。
4. **红线核对**（这是本项目评审独有的一步，不能省）：
   - 红线 10：diff 里新增的任何中文长段样例、`tests/fixtures/` 下的文件，必须是
     合成的（内容明显是编的、或文件头写明合成来源）。像真实直播转写的一律按
     违规处理：删掉、换合成的、补测试。
   - 红线 2 / 3 / 5：闸门只删不改、只报警不修正；渲染不改写整理层文字；核查层
     不动整理层字段。diff 里出现「顺手修正模型输出」的逻辑就是方向错误。
   - 红线 9：新产生的派生文件带 provenance；失败单元进 `_failed/`，没有静默 `continue`。
5. 检查是否有与 issue 无关的改动混入。（评审也不要读 `.sandcastle/`；diff 里
   若出现对它的改动，按无关改动处理。）
6. 若 diff 改了 `prompts/*.md`：首行 `version:` 必须升；没升直接补
   （计入 `review:` commit）。
7. 若 diff 新增 / 删除 / 重命名了 `scripts/`、`prompts/`、`pc/` 下的文件，或改了
   某层的输入输出文件、字段、闸门规则：`SPEC.md` 对应条目必须在同一分支里同步
   （只写「做什么」）。契约变了 SPEC 没跟，算验收缺口，直接补。纯逻辑改动不涉及。
8. 核对 `docs/qa/issue-{{ISSUE_NUMBER}}.md`：必须存在；「可见变化」演示必须在——
   自己在 fixture 副本上重跑 issue 里那条演示命令，产出要和 QA 文档贴的一致、和
   issue「可见变化」一节描述的一致（这是纵切票的验收核心，不是附录）；「已验证清单」与实际
   测试一致；「真实样例验证指引」必须真的能触发本次 diff 改动的代码路径
   （对照 diff 检查命令、参数、文件名、期望形状是否准确），且包含回退说明。
   缺失或失实的直接修好（计入 `review:` commit）。
9. 写 PR 摘要（见下），作为 `review:` commit 的一部分提交。

## PR 摘要（必交）

写 `docs/qa/issue-{{ISSUE_NUMBER}}-brief.md`，它会被贴在 PR body 最顶部。

它只有一个读者：**要在几分钟内决定合不合的人**。它不是 QA 文档的缩写版，是
另一个海拔——QA 文档答「改了哪些文件、哪条验收标准对应哪个测试」，这份答
「这件事为什么值得做、做成了没有、哪里最可能出事」。

**你是流程里唯一适合写它的人**：实现 agent 泡在自己的上下文里，分不清什么
重要，也倾向于罗列自己干了什么；而你是冷读 issue + diff 的，视角和打开 PR
的人相同。

严格用下面四个小标题，**全文 300 字以内**：

```
## 为什么做
issue 想解决的真实问题——不是「实现 X 功能」，是「不做会怎样」。

## 改了什么
概念层的一两句话。禁止列文件名，禁止贴代码。

## 效果
合并后能观察到的差别（跑哪层会多出什么文件、闸门会多拦什么）。若无外部可见
变化，直说「纯内部改动，外部行为不变」。

## 最大风险
一到两条。每条必须答清两件事：**它错了会怎样**、**怎么第一时间发现**。
不写「需注意 X」这种没有动作的话。确实没有就写「无」——但先想清楚再写。
```

硬性禁止：复述验收标准清单、整段复制 QA 文档、超过 300 字。宁可少写一条，
不要写成第二份 QA 文档——那样它就白加了。

## 处置

- 发现问题：直接修复并补测试，以独立 commit 提交（message 前缀 `review:`）。
- 无法修复的根本性偏差（实现方向错了、或触犯红线且改法等于重写）：不要重写，
  输出 `<promise>REJECTED</promise>` 并在最后清晰列出偏差点。
- 全部验收标准通过、测试绿、红线核对无违规、且
  `docs/qa/issue-{{ISSUE_NUMBER}}-brief.md` 已提交：输出
  `<promise>COMPLETE</promise>`。摘要没提交就不算完成。
