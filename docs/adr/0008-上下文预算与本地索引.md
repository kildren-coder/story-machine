# 0008. 上下文预算与本地索引：每次调用不超 12 万，输入不随历史涨

**Date:** 2026-10-20（决定形成于 2026-10-14 至 10-20）
**Status:** Accepted

## Context

ADR 0004 定了一层一个无头调用，没有定每次调用能吃多少。2026-10-14 用户定下**每次调用 12 万 token 为目标、15 万为硬上限**，深加工也算在内。拿原型量了一遍峰值（写进缓存的加输出）：

| 调用 | 峰值 |
|---|---|
| L1 切章，EP01 | 约 5.3 万 |
| L1 切章，EP02（3 小时 10 分） | 约 8.7 万 |
| L2 一章 | 约 1.8 到 7 万 |
| 挂述线（原型一次调用） | 约 1 到 1.5 万 |
| 深加工核查，一条两集的述线 | 约 8.8 万 |
| 深加工四问，同一条 | 约 9.3 万 |

眼下都在 12 万以内，但有两处会随输入涨：L1 随集长，约 2.4 万一小时，超过约 4.5 小时的集就过线；深加工随述线挂的段数涨，只挂两集已近 9 万。

挂述线那层原来的设计也在涨：一次调用看**全部**已有述线的清单，再加一个「近期没挂的旧段」的池子让模型回挂。池子按字数封顶 3 万字（实测每集没挂的头 EP01 8 条约 1000 字、EP02 19 条约 2800 字），池子外更早的就看不到。2026-10-17 用户问：积累多了，回挂要看的越来越多，是不是该先粗筛再细判。

另一处是 10-20 议正字时暴露的：我按「每晚一集一次调用、一集封顶若干条联网」设计，用户指出一集可以长达五小时、「一集」定义模糊，要按**处理无限输入**来想。

## Decision

1. **预算是硬规矩。** 每次模型调用以 12 万 token 为目标、15 万为硬上限，含深加工。代码在调用前按字数预估，超了先切片；调用后记实测峰值，过 12 万告警。L1 的切片法：按预算把逐字稿切成几片，约 4 小时一片，十小时就是三片，片数由代码按预算算、不写死；切口选目标点前后最长的停顿；每片单独切章，章表由代码拼接，片界就是章界。一章被切成两章只是容器层面的小代价，L2 照常。
2. **模型的输入不随历史变长。** 会变长的只有**本地索引**：关键词加向量，每个述段生成时建一次，本机跑、不花额度，宁多勿漏。模型只看检索排在前面的那一批。
3. **挂述线拆成三次小调用，步与步之间走本地检索，每步的输入都不随历史涨。** 工作项是一集的述段头（标题、一句说明、主段或旁段、时长；十小时的集约 150 段、不到 2 万 token），一次运行有几集就按集排队。
   - **4a 认事**：输入这一集全部述段的头，不看任何已有述线。输出这一集谈到的几件事，每件给名字、一句说明、属于它的述段 id；一段可以在几件里。
   - 检索一：每件事拿名字加说明去述线索引，取最像的约 5 条已有述线，含同一次运行里前面几集刚开的。
   - **4b 对已有的**：每件事只看自己那约 5 条候选，判它是已有的哪条还是新的。是已有的就挂上去，每段按「能帮人理解这条述线」判。
   - 检索二：每件新的事去述段索引取最像的一批旧述段，按预算封顶。述段索引是全部历史，主段旁段、已挂没挂都在。
   - **4c 拉旧的**：每件新的事只看自己的旧述段候选，判哪些旧述段也属于它，再按开线的尺子（0007 第 4 条）判加上旧的够不够开一条线。够就开线，新旧述段都挂上，旧的标「回挂」；不够就都留在没挂的述段里，等以后再被 4c 找到。4c 当次生效、只加挂不改挂、不用人点头。
   - 人预开的述线、回顾整体拆出的述线当新的事走检索二和 4c。**3 万字池子作废**，它的两件事都归检索二。
4. **「先召回、再细判」是通用形状，封顶按预算定。** 封顶 = 一次调用装得下的述段头条数，由 12 万预算减去固定部分算出来，头约 100 字一条，具体值由调研票定；段数超过封顶的述线叫大述线，DSA 一年几百段就是。新线回扫、回顾整体的配对与拆分、没挂的述段整成述线、以后深加工里的说法匹配，都是第一步本地索引召回、第二步模型只看候选。大述线先在索引里按相似度聚堆，模型只看每堆几段和代表性的头。
5. **索引和向量模型放 5070。** 笔记本经 Tailscale 发述段的头和查询、收回 id，用小 HTTP 服务或脚本文件，不在 ssh 命令行拼长参数。索引是派生物，丢了从 vault 重建、不备份。5070 没开时这一集先不挂述线，整理稿照进 EP 笔记，下次运行补挂。
6. **工作单位是队列里的小项，不是「集」。** 任何阶段先回答三件：工作项是什么（词、说法、述段、问题轮次）、缓存在哪（词表、说法台账、问题的账）、额度旋钮在哪（面板）。批按 token 切，队列按优先级排，没做完的顺延，产物先可用、再升级。「集」只用作锚点（`EP02@HH:MM:SS`）和阶段 0 的转写容器，不是任何阶段的预算单位。
7. **MVP 直接用索引**，不走「先全给、以后再加索引」。检索工具另开调研票：候选 qmd、本地向量模型，必要时试 5070 上的本地大模型做第一步；基准不是原型旧规则的挂法，而是两集按新规则由模型一次看全挂出来、再经人核过的挂法，含多挂与旁段，即核实清单里各条「EP02 应为」；量两件事：索引召回（基准里每条述线的述段是否都进前 N 条）和 4a、4b、4c 走检索的结果与基准的一致率；要测音译异写（同一人名两种写法）、主播自造词、缩写与全称，关键词与向量各自漏什么；中文切词要验；聚堆准不准与封顶值一起测。

## Rationale

**为什么要一个数。** 超长输入质量先掉、费用后到，订阅额度又和夜跑、子代理共用一个池子。有了数，每层才能预估、分段、告警，而不是跑到失败才知道。

**为什么是索引，不是「把清单都给模型」。** 述线清单和没挂的旧段只会越来越多，给全量就是 ADR 0004 警告过的「拿着一堆东西自由发挥」，而且花的是额度。索引在本机，零额度，可以宁多勿漏；模型只做需要判断力的那一步。用户定 MVP 就用索引，理由是早发现问题，比先堆一个会长大的清单再回头改便宜。

**为什么拆成三次。** 一次调用既要认今晚的事、又要对全部旧线、又要回挂旧段，三件事的输入都随历史涨。拆开以后每次的输入都是「今晚的 + 检索出的少数几条」，谁都不涨；3 万字池子那种「按字数封顶往前翻」的补丁就不需要了。

**为什么放 5070。** 索引本身很小（每集不到 0.3 MB），占地方的是向量模型和本地大模型，本来就该在显卡上跑；笔记本两个盘各剩三四十 GB，vault 已 224 MB、多是音频（音频搬去 5070 另有 #93）。

**为什么不按集。** 五小时的直播和二十分钟的视频都是「一集」，工作量却不跟时长走：聊老话题的长直播可能只冒出两个生词，聊新话题的短视频可能冒出十五个。按集定预算，长集爆、短集浪费，还把「集」偷偷变成了处理单位。按项排队、按额度消化，输入永远有界。

## Consequences

- `SPEC.md` §4.1 写进预算规则、预估与实测记录、告警；§7 的 model / effort 表加预算列。
- L4 事件层换成 4a / 4b / 4c 三次调用，各自有输入输出文件、各留 `_pairs/`；L1 加按预算切片与章表拼接。
- 新部件：5070 上的索引服务（建索引、查询、聚堆），笔记本侧的客户端；PC 侧改动合并前必须在 5070 真跑。
- 夜跑多了一个依赖：5070 不在线时挂述线这一步跳过、下次补，整理稿不受影响。
- 调研票先行；它的结论（工具、向量模型、召回率、聚堆封顶）决定第 4 步那张票的具体做法。
- **2026-10-25 补记（#95 检索调研结论，用户定）**：调研票 #95 已关。两集基准 `baseline-95@0.3`（97 个述段、27 条述线、147 条挂法，主 81 / 兼 66，两轮人核定稿）在本机量完，全程零模型额度。定下九处：
  1. **第一步工具**：混合 = Qwen3-Embedding-0.6B 向量 + 字二元 BM25，RRF 合并，自己跑、不经 qmd。四家向量模型差不到 5 个点，工具不是关键，索引里放什么和 N 才是；混合在 N 小的时候最稳。
  2. **索引放述段头加正文，查询只用头或一句说明**：比只放头多 4 到 6 个点。第 5 条「笔记本发述段的头」改成「发头和正文」。
  3. **述线索引 k=5**（检索一）：基准上 k=3 已全中。
  4. **述段索引每件事取前 50、不足全给，封顶 600 条紧凑头**（检索二，第 4 条的封顶值）：述线 → 述段 N=20 95%、N=30 98%、N=50 100%；跨集回挂向量 N=20 97%、N=30 98%，关键词只有 80%。一条头用紧凑 id `EP02@HH:MM:SS` 约 138 token，50 条约 7000 token，12 万预算扣 2 万固定部分装 727 条。
  5. **大述线聚堆**：头向量平均连接、余弦距离阈值 0.5 起步按堆数调；两集样本的堆按事分、不按集分，真大述线再量准确度。
  6. **重排不上**：bge-reranker-v2-m3 不提高。
  7. **本地大模型不做第一步**：Qwen3-14B 看全部头挑，召回 71%、精确 36%、每条述线 54 秒。
  8. **qmd 不用**：search 的 FTS5 词与词 AND，中文长查询零结果；vsearch 换成同一个 Qwen3 模型仍比自己跑低 2 到 3 个点、比混合低 6 到 9 个点；query 模式不加分、每次 20 到 50 秒。
  9. **词表接进检索**：N=20 漏的 8 条是自造词 2、历史案例说法差得远 2、只提一句的兼 4，异写与缩写 0；对照实验抹掉一种写法，缩写关键词掉 3 到 7 名、小向量模型也掉，自造词两家都掉。缩写全称、自造词、异写记进 0010 的词表，查询时同组写法都带上并当实体键。
  - **兼的门槛**（基准人核时定，是 0007 第 3 条「顺嘴一提的不挂」的尺子）：兼要有一个判断加理由、或一件事的经过；一句提及、复述上一段、预告、提问都不算。
  - **实现时带召回抽检**：基准只有两集，N=50 全中是在 97 段里挑的，库到几百段后同样的 N 够不够要在真数据上看。第 4 步实现票把每条挂法回查一次排名记日志；人手补的挂也查当时排第几，排在 N 外算检索漏、N 内算模型漏。换 N、换模型、换精度用同一套量法重量，全库重算向量不到一分钟。Qwen3-Embedding-4B 比 0.6B 只多 2 个点、占 8 GB 显存，留作后手，不预先量化，量化前先量损失。
  - 说法匹配（0013）可复用同一套，要补数字规范化与实体键过滤，先记不做。基准、脚本、报告留本机 `_lab/thread-proto-20261009/retrieval-95/`（含整理稿片段，不入库）；仓库只进计数与合成样例。
- 以后每个新阶段的设计都要先答「工作项、缓存、旋钮」三问；正字（0010）、说法匹配与说法台账（0013）照此。
- 样例一律合成（红线 10）：召回率用两集真实挂法在本机量，仓库里只放合成样例和计数。
