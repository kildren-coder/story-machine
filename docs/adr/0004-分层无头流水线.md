# 0004. 分层无头流水线：一层一个调用，闸门在代码里

**Date:** 2026-09-12
**Status:** Accepted

## Context

**LLM 走哪里，2026-07 已经定了。** #14 用同一分块、同一 prompt、同一 schema 实测三个引擎：Gemini Flash 只抽出 5 条关系 / 6 条论断（实体 40 条与本地模型持平）——能答「出现过谁」，答不出「论证了什么」；本地 Qwen3-14B-Q4_K_M 的 40 条实体里 11 条引文查无此句。结论是**分块结构化提取不是机械性任务，不适合拿免费额度换**，全流程 LLM 统一走笔记本上的 Claude Code 订阅，形状是无头调用 `claude -p --model … --effort … --allowedTools ""`（禁用 `--bare`，它计到 API credits 而不是订阅额度）。`scripts/stage12.py` 在 2026-08-12 落地了这个形状，EP03 单块 242 秒，原始响应留档支持 `--replay` 免额度重渲染。

**怎么切任务，是 2026-09-11 原型逼出来的。** 那天派 sonnet 子代理把 EP02 按 60 分钟一块、一口气各写成整理稿：三块分别跑了 33、47、34 分钟，119k 到 242k token；其中一版让模型自己核对引文，用了 88 次工具调用；另一版超过 64k 输出 token 上限直接失败；此前五个默认继承 Fable 的子代理几分钟烧光了月度额度。用户的评价：「你似乎是让子代理一口气去做了大量的工作，没有将工作分层，我的想法是整个流程会分为好几层，前一层的结果是后一层的输入」，并要求「事实核查或者需要深度思考的地方应该加大思考深度，相对简单的工作才用低思考深度」。

顺带测过一个疑问：逐字稿里的时间戳是不是在浪费输入 token。EP02 每段一个 `[HH:MM:SS] 说话人:` 前缀占输入约 6.9%；改成每分钟一个戳、说话人只在变化时标，降到 2.9%。这不是杠杆，只是一个免费的小改。

## Decision

1. **流水线是一串无头调用。** 每一层有明确的输入文件和输出文件（JSON 或 markdown），切片和拼装由代码做。生产流程里没有「拿着整集逐字稿自由发挥」的大任务，也不用 Agent 工具的子代理（子代理只在交互会话里做原型和调研，且必须显式指定 model）。
2. **层与思考深度**（起手值，实跑后调）：

   | 层 | 做什么 | 输入 | model / effort |
   |---|---|---|---|
   | L1 骨架 | 话题表：编号、标题、时间范围、谁在说、一句话 | 整集逐字稿（压缩格式） | sonnet / low |
   | L2 逐话题整理 | 讲了什么（全长）、原话锚点、可核查的说法、提到的信源 | **该话题的切片**（前后各留 2 分钟） | sonnet / medium |
   | L3 闸门 | 引文逐字命中、时间戳在范围内、限定词保留、schema | L2 输出 + 逐字稿 | 纯代码 |
   | L4 事件 | 当天事件清单，跨 EP 聚类，主次引用 | 各 EP 的话题表 + 可核查的说法 | sonnet / medium |
   | L5a 事实核查 | 逐条判定 ok / warn / bad / none + 依据 + 链接 | 一个事件的可核查说法 | sonnet / **high**，联网 |
   | L5b 证据·先例·分析 | 支持 / 不支持 / 先例 / 当时 vs 现在 / 有见地的读法 | 一个事件的整理稿段落 + L5a 结果 | **opus / high**，联网 |
   | L6 导语与对照 | 日报导语；跨 UP 对照表由代码拼 | 事件清单 + 各卡 | sonnet / low |
   | L7 渲染 | 日报笔记、事件笔记更新 | 全部中间产物 | 纯代码 |

3. **机械可判的事不交给模型。** 引文是否逐字出现在逐字稿段落里、时间戳是否落在话题范围内、限定词有没有被丢掉、JSON 是否合 schema——全在 L3 用代码判。模型不自校验。
4. **每层留三份**：原样输入（`_pairs/`）、模型原始响应、解析后的产物。失败只重跑失败的那一层。
5. **喂给模型的逐字稿格式**：保留 30 秒级时间戳，说话人只在变化时标注。不做更激进的压缩——时间戳是回到原话的唯一线索。

## Rationale

**输出长度是瓶颈，不是输入。** 一次生成 12,000 字的整理稿，无论模型多快都是半小时量级，而且一处出错整篇重来。按话题切成十来段、每段一千字，可以并行、可以单独重跑、可以单独做 golden 测试。

**分层才能分配思考深度。** 整集一次调用只能选一个 effort：选 high 是把骨架这种低难度活也按高价跑，选 low 是把核查按低价跑。分开之后，high 只花在核查和分析这两层上。

**模型自校验又贵又不可靠。** 88 次工具调用换来的核对，代码一个循环零额度做完，而且结果是确定的。ADR 0002 的原则在这里同样成立：状态和判定落在文件和代码里，模型只做需要判断力的那一步。

**前一层输出即后一层输入，是可测试性的前提。** 2026-07 断言表阶段留下过一条教训（#48）：漏项是任务框定漏洞，不是容量问题，缩短块长是拧错旋钮；正解是把规则写进带版本的 prompt，用真实一集当 golden 样例对照重跑。分层让每一层都能这样测。

## Consequences

- 中间文件变多（话题表、话题片段、事件清单、核查 JSON），都落在 vault 的 `_pairs/` 和 `_pipeline/` 下，**人不看**（阅读负担红线）。
- prompt 按层分文件（`prompts/L1-skeleton.md` 等），带版本号；`prompts/stage2-extract.md` 2026-09-12 已删（取回：`git show 3b0e9b9:prompts/stage2-extract.md`），其中引文逐字、不脑补、限定词原样保留三条规则搬进 L2。
- `stage12.py` 的分块、无头调用、闸门、留档四块直接复用；分块粒度从「20 到 30 分钟一块」改为「按话题切」。
- 跨 UP 的事件聚类（L4）是承重层：聚错一个事件，六问卡和对照表都跟着错。它需要自己的 golden 样例。
- 队列状态机是否从阶段 0 延伸到 L1 到 L7 未定，定了补记 ADR 0002。
- 额度参考：原型里三块整理（含自校验）约 49 万 token，三个事件的核查各约 10 万 token。分层后整理部分应明显低于此，核查部分不变。
